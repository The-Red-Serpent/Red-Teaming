Active Directory supports certificate-based authentication through two important mechanisms:

    PKINIT – Certificate-based initial authentication using Kerberos.

    Schannel – Certificate-based authentication over TLS/SSL connections.

Both use X.509 certificates, but they authenticate users through different protocols.


# PKINIT – Certificate-based Kerberos authentication

PKINIT allows a user to authenticate directly to the KDC using a digital certificate and its corresponding private key.

The process is:

    The user has a certificate issued by ADCS.

    The certificate contains the user's public key and identity information.

    The user sends an AS-REQ containing PKINIT authentication information.

    The KDC validates the certificate and verifies possession of the corresponding private key.

    If authentication succeeds, the KDC issues an AS-REP containing a TGT.

Result: The user obtains a Kerberos TGT.

This means the user can subsequently request service tickets and access domain resources.

# Schannel – Certificate-based TLS authentication

Schannel is Microsoft's Windows implementation of TLS/SSL through its Security Support Provider architecture.

It can also support certificate-based client authentication.

For example, imagine an organization has an internal LDAP server that supports LDAPS.

The authentication process is:

    A client connects to the LDAP server using TLS.

    The server requests a client certificate.

    The client presents its certificate.

    The server validates the certificate and its trust chain.

    The server attempts to associate the certificate with an Active Directory account.

    If the certificate is successfully mapped and authentication is accepted, the client is authenticated.


Notice the difference:

    - PKINIT authenticates the client to the KDC and obtains a TGT.

    - Schannel authenticates the client to a TLS-enabled service, such as an LDAPS server.

Schannel authentication does not automatically provide a Kerberos TGT
