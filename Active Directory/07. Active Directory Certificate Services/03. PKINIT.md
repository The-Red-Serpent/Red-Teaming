# PKINIT
PKINIT (Public Key Cryptography for Initial Authentication) is an extension of the Kerberos 5 authentication protocol that replaces traditional password-based pre-authentication with X.509 public key certificates. Instead of proving its identity using only password-derived information, the client proves possession of a private key associated with a trusted digital certificate.

PKINIT uses:

    Digital certificates (X.509).

    Public-private key pairs.

    Certificate Authorities (CAs).

    Digital signatures.

    Public-key encryption or key agreement.

    Kerberos authentication messages.

Main idea:

- The user has a digital certificate containing their public key, while the corresponding private key is securely stored on their device, smart card, or other cryptographic storage.

- The KDC validates the certificate and verifies the client's proof of private-key possession.

- If authentication succeeds, the KDC issues a normal Kerberos Ticket Granting Ticket (TGT).

# PKINIT Authentication 

Suppose an organization has the following environment:

| Parameter | Value |
| --- | --- |
| Domain | `example.com` |
| User | `alice@example.com` |
| Domain Controller | `DC01.example.com` |
| Authentication Method | Smart Card Authentication |
| Certificate Authority | Enterprise CA |
| Protocol | Kerberos with PKINIT |

Alice wants to log in to a domain-joined Windows computer using her smart card instead of entering her normal domain password. The following steps take place.

## Step 1: User Receives a Digital Certificate

Before authentication, Alice must have a suitable digital certificate.

The organization issues this certificate through its Enterprise Certificate Authority (CA).

The certificate contains:

- Alice's identity information.
- Alice's public key.
- Certificate issuer information.
- Certificate validity period.
- Key Usage and Extended Key Usage (EKU).
- CA's digital signature.

The corresponding private key is securely stored on Alice's smart card.

### Understanding the Keys

Alice has two cryptographic keys:

Private Key:

- Stored securely on the smart card.
- Must never be shared.
- Used to sign authentication data.

Public Key:

- Included in Alice's digital certificate.
- Can be shared with the KDC.
- Used by the KDC to verify Alice's digital signature.

The CA also has its own key pair:

- CA Private Key: Used to sign Alice's certificate.
- CA Public Key: Used to verify the CA's certificate signature.

Important: The CA's private key and Alice's private key are two completely different keys.

## Step 2: Client Sends AS-REQ to the KDC

When Alice attempts to log in, her computer contacts the Domain Controller's KDC.

The client sends an Authentication Service Request (AS-REQ).

In PKINIT, the AS-REQ contains special pre-authentication information called:

`PA-PK-AS-REQ`

This information includes an AuthPack containing cryptographic authentication data.

It can include:

- Client's public-key-related information.
- Timestamp and other authentication data.
- A digital signature generated using Alice's private key.
- Client certificate information and supporting certificates, where included.

### Why Does the Client Sign the Request?

The digital signature proves that Alice possesses the private key corresponding to the public key in her certificate.

The KDC can verify this signature using Alice's public key.

This is important because simply sending a public certificate does not prove that the sender owns the corresponding private key.

Remember:

- Alice signs using her private key.
- The KDC verifies using Alice's public key.

## Step 3: KDC Validates the Client's Certificate and Identity

The Domain Controller receives the AS-REQ and performs several validation operations.

### A. Certificate Chain Validation

The KDC checks whether Alice's certificate is issued through a trusted certificate chain.

For example:

- Is the certificate issued by a trusted CA?
- Does the certificate chain lead to a trusted root CA?
- Is the certificate within its validity period?
- Does it have appropriate Key Usage and EKU?
- Is it revoked, according to the applicable revocation policy?

The KDC uses trusted CA public keys to verify the digital signatures on the certificate chain.

### B. Digital Signature Verification

The KDC verifies the signature included in Alice's PKINIT authentication data.

It uses Alice's public key to verify the signature.

If verification succeeds, it demonstrates possession of the corresponding private key.

### C. Identity Mapping

The KDC must determine which Active Directory account corresponds to Alice's certificate.

It can use certificate identity information such as:

- Subject Alternative Name (SAN).
- User Principal Name (UPN).
- Subject information.
- Explicit certificate-to-account mappings.

The KDC also checks the certificate against applicable account and authentication policies.

### Result

If certificate validation, signature verification, identity mapping, and other authentication checks succeed, the KDC accepts Alice's certificate-based authentication.

Important: Certificate validity alone does not automatically mean that the certificate is authorized for a particular Active Directory account.

## Step 4: KDC Sends AS-REP to the Client

After successful authentication, the KDC generates an Authentication Service Reply (AS-REP).

The AS-REP contains:

- Ticket Granting Ticket (TGT).
- Kerberos session key information.
- Additional authentication information.

The important question is:

How does the KDC securely deliver the AS reply key to the client?

PKINIT supports two main mechanisms.

### Method A: Diffie-Hellman Key Agreement

Diffie-Hellman allows two parties to establish a shared secret over an insecure communication channel.

In PKINIT:

1. The client and KDC exchange Diffie-Hellman public values.
2. Both independently calculate the same shared secret.
3. They derive the AS reply key from that shared secret.
4. The KDC signs the relevant key-exchange information using its private signing key.
5. The client verifies the KDC's signature using the KDC's public key.

The shared secret is not directly transmitted over the network.

Purpose: It allows the client and KDC to establish shared cryptographic key material without directly transmitting the secret.

### Method B: Public-Key Encryption

Another supported mechanism uses public-key encryption.

The process is:

1. The KDC generates a temporary symmetric key.
2. The KDC encrypts that key using Alice's public key.
3. The KDC signs the relevant response information using its private signing key.
4. Alice uses her private key to recover the temporary key.
5. Alice verifies the KDC's signature using the KDC's public key.

Purpose: It allows the KDC to securely deliver the key material to the authenticated client.

### Important Distinction

| Diffie-Hellman | Public-Key Encryption |
| --- | --- |
| Establishes a shared secret through key agreement. | Protects key material using public-key encryption. |
| Both parties calculate the shared secret. | The KDC generates the key material. |
| KDC authenticates its key-exchange information through its signature. | KDC signs the relevant response information. |

## Step 5: Client Verifies the KDC

PKINIT also provides a mechanism for the client to authenticate the KDC.

This is called mutual authentication.

The client receives the KDC's certificate and validates it.

The validation includes:

- Certificate issuer and trust chain.
- Certificate validity period.
- Appropriate key usage and EKU.
- KDC identity and applicable realm validation.
- Certificate signature verification.

The client uses the trusted CA public key to verify the KDC certificate chain.

It then uses the KDC's public key to verify the KDC's digital signature on the relevant PKINIT response information.

### Key Concept

There are two different signature-verification operations.

Operation 1: KDC Certificate Verification

- CA signs the KDC certificate using the CA's private key.
- Client verifies the certificate using the CA's public key.

Operation 2: KDC Response Verification

- KDC signs PKINIT response information using its private key.
- Client verifies the response signature using the KDC's public key.

Do not confuse these two operations.

## Step 6: Client Decrypts the AS-REP and Obtains the TGT

After establishing the AS reply key, the client processes the encrypted portion of the AS-REP.

It obtains:

- Kerberos session key.
- Ticket information.
- Other authentication data.

The TGT itself is encrypted using the KDC's `krbtgt` account key.

This is an important distinction:

| Information | Protection |
| --- | --- |
| AS-REP encrypted portion | AS reply key |
| TGT | KDC's `krbtgt` key |

The client stores the TGT in its Kerberos ticket cache.

Initial Authentication SuccessfulAlice has now successfully completed the initial Kerberos authentication using PKINIT.

She can now use her TGT to request service tickets.

# 6. What Happens After PKINIT Authentication?

This is one of the most important concepts to understand.

PKINIT is used during the initial Kerberos authentication (AS exchange).

After obtaining the TGT, the client follows the normal Kerberos authentication process.
