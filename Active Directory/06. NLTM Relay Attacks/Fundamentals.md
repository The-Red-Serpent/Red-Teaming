## Message Signing
Message signing is a security mechanism that protects the integrity of communication between a client and a server. In Active Directory environments, you'll commonly encounter it with SMB and LDAP.When a client and server establish an NTLM-authenticated session, they can negotiate whether message signing will be used. If signing is negotiated and required, both sides establish the necessary cryptographic signing keys using session-key material derived from the NTLM authentication process.

Once the session is established, whenever the client sends a message, it calculates a Message Authentication Code (MAC) using the message contents and the signing key. This MAC is attached to the message.When the server receives that message, it independently calculates the expected MAC using its corresponding signing key. It then compares its calculated MAC with the MAC received from the client. If they match, the message passes integrity verification. If they don't match, the message is rejected.

The same principle applies to messages travelling in the opposite direction.

This makes it difficult for an attacker to modify communication without detection because the attacker doesn't possess the necessary signing key.
NTLM message signing is a mechanism that  provides message integrity and helps mitigate certain NTLM relay attacks by allowing the client and server to verify that messages have not been modified after authentication. It does not encrypt the message itself that is the job of NTLM sealing.

When NTLM message signing is enabled, the client and server first agree to use signing during the NTLM authentication process. After successful authentication, both sides independently derive the same session key using the client challenge, the server challenge, and information derived from the user's password hash. Importantly, the password hash is never sent across the network; each side computes the session key locally. Once the session key is established, all messages between the client and server are signed using a MAC. The MAC is generated by applying a cryptographic algorithm to the message and the session key. The server can verify the MAC by using the same algorithm as the message and the session key and comparing the result to the MAC provided by the client. If the server's computed MAC matches the one received from the client, it knows the message has not been altered and was sent by someone who possesses the correct session key. If an attacker intercepts and modifies the message, the original MAC will no longer match the modified message. Since the attacker does not know the user's password-derived secret and therefore cannot derive the session key, they cannot generate a valid MAC, causing the server to detect the tampering and reject the message.

## Limitations
- Signing does not encrypt the message. The message contents may still be readable.

- Signing does not prevent an attacker from relaying NTLM authentication itself.

- It protects the session, not the original NTLM authentication exchange.

- It only protects protocols and sessions where signing is supported and actually enforced.

- If signing is optional and not required by the target, the session might proceed without signing.

## Message Sealing
Message sealing in NTLM is the process of encrypting messages exchanged between the client and server so that an attacker who captures network traffic cannot read the contents. While message signing provides integrity (detects if a message was modified), message sealing provides confidentiality (keeps the message secret). After NTLM authentication, the client and server already have a shared session key. From this session key, they derive separate sealing keys that are used for encryption.

## MIC (Message Integrity Code)

MIC protects something different: the NTLM authentication exchange itself.

To understand this, remember that NTLM authentication consists of three messages. The client first sends a Type 1 NEGOTIATE message containing its supported security capabilities. The server responds with a Type 2 CHALLENGE message containing its challenge and negotiated capabilities. Finally, the client sends a Type 3 AUTHENTICATE message containing its authentication response. These messages contain important security information, including negotiation flags. An attacker who can modify these messages might attempt to manipulate the authentication negotiation.

MIC exists to protect the integrity of this exchange.

During authentication, the client calculates a MIC using HMAC-MD5, with the appropriate NTLM session key and the three authentication messages as inputs. The MIC field is zeroed when calculating the value for the Type 3 message. The resulting MIC is included in the Type 3 AUTHENTICATE message.

When the server receives the final message, it independently calculates the expected MIC using the corresponding session key and the authentication messages it received. It compares this value with the supplied MIC.

If someone has modified one of the protected authentication messages, the calculated MIC will no longer match the received MIC. The server can therefore detect that the authentication exchange has been tampered with.


How does this stop relay attacks?

The important thing to understand is that relaying and modifying are two different things.

- Pure relay: The attacker forwards the NTLM messages without modifying them. MIC does not stop this because the original MIC remains valid.

- Modified relay: The attacker changes authentication negotiation information, such as removing signing-related flags. MIC detects the modification and causes authentication to fail.

So what are MIC's limitations?

MIC does not: 
- Stop an attacker from forwarding unmodified NTLM authentication messages.

- Encrypt NTLM authentication messages.

- Protect the session after authentication.

- Replace SMB signing or EPA

## EPA (Extended Protection for Authentication)

EPA addresses another weakness in authentication protocols: authentication can potentially be forwarded to a different service or connection.

Unlike MIC, which protects the integrity of the NTLM authentication messages, EPA attempts to establish a relationship between the authentication and the destination or communication channel for which it was originally intended.

EPA has two important mechanisms: Channel Binding Token (CBT) and Service Binding.
Channel Binding Token (CBT)

CBT is primarily relevant when authentication happens over TLS connections, such as HTTPS and LDAPS.

When a client establishes a TLS connection with a server, the TLS connection has its own cryptographic characteristics, including information associated with the server's certificate.

The client obtains channel-binding information associated with that TLS connection and includes it in the NTLM authentication data.

This information is protected by the NTLMv2 cryptographic response.

When the server receives the authentication request, it obtains the expected channel-binding information from its own TLS connection and compares it with the information supplied by the client.

If the information doesn't match, authentication can be rejected.

This is what makes CBT useful against NTLM relay. Authentication is no longer treated as something that can freely move between different TLS connections.

One limitation is that CBT requires a TLS channel. It cannot provide TLS channel binding when there is no TLS connection. Also, both the client and server must support the required functionality, and the server must enforce the relevant EPA policy.
Service Binding (SPN)

Service binding protects the identity of the service to which authentication is intended.

An SPN, or Service Principal Name, identifies a service instance in Active Directory. Examples include:
text

```
HTTP/server01.domain.local

LDAP/dc01.domain.local

CIFS/server01.domain.local
```

With EPA service binding, service identity information is included in the authentication data.

The information is cryptographically protected as part of the NTLMv2 response. The receiving service can then validate whether the authentication is intended for the service it actually provides.

If the service identity doesn't match the expected destination according to the server's EPA policy, authentication can be rejected.


## Conclusion
. MIC – Protects authentication

MIC protects the integrity of NTLM authentication messages.

It prevents an attacker from modifying those messages while relaying them.

However, if the attacker forwards the messages without changing anything, MIC can still validate successfully.

So MIC does not stop pure NTLM relay.
2. SMB/LDAP Signing – Protects the session

This is where your understanding needs a little adjustment.

Signing protects the communication that happens after authentication.

If a server requires signing, the attacker cannot simply authenticate as the victim and start sending commands or requests because they cannot generate valid signatures without the required session key.

So signing can allow authentication to happen but prevent the attacker from using the resulting session.
3. EPA – Protects authentication from being relayed to the wrong destination

EPA binds NTLM authentication to the intended service or TLS channel.

If an attacker tries to forward authentication to a different service or TLS endpoint, the binding information won't match, and authentication can be rejected.

So EPA can stop the relay before authentication succeeds.
